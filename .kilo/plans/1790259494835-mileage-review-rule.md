# План: правило «пробег не больше 400 000 км, иначе review»

Контекст: решение сейчас зависит только от LTV (`DecisionEngine::decide()`, backend/src/Domain/DecisionEngine.php:30). Пробег лишь валидируется в `ApplicationValidator.php:43-46` по `max_mileage_km = 500000` (backend/config/rules.php:23) и не влияет на решение. Новое правило — правило решения, а не валидации: в `ApplicationValidator` его класть нельзя (ошибка там = HTTP 422 без решения).

Решение по семантике (принято для плана, подтвердить у заказчика — см. Вопросы):
- Граница: «не больше 400 000» → пробег ≤ 400 000 — без изменений; 400 001 и выше — `review`.
- Правило только понижает `approve` → `review`; `reject` не смягчает (reject по LTV остаётся reject при любом пробеге).
- Пустой/отсутствующий пробег остаётся ошибкой валидации (HTTP 422) — текущее поведение не меняем.

Примечание: целевой путь `docs/plan/plan_MILEAGE.md` (по AGENTS.md) недоступен по правам этого агента — план сохранён в `.kilo/plans/`; при реализации скопировать в `docs/plan/plan_MILEAGE.md`.

## 3. Тесты

Граничные значения — отдельной строкой:
- 399999 км + LTV 50 → `approve`, лимит = сумме;
- 400000 км + LTV 50 → `approve` (граница «не больше» — включительно);
- 400001 км + LTV 50 → `review`, лимит 0;
- пустой пробег (поле отсутствует / null) → `ValidationException`, HTTP 422, решение не считается.

Дополнительно:
- 450000 км + LTV 95 → `reject` (правило не смягчает reject);
- 450000 км + LTV 75 → `review` (как было, без изменений);
- существующие тесты `AssessmentServiceTest` (пробег 96000) должны остаться зелёными без правок.

Тесты на `decide()` в `DecisionEngineTest` (Unit): границы 399999/400000/400001 с LTV ниже approve_max.

## 4. Риски

- **Существующая проверка `max_mileage_km`**: остаётся (0…500 000 → 422). Интервал действия нового правила фактически 400 001…500 000; всё выше 500 000 отсекается валидацией раньше и до `decide()` не доходит. Смешивать два порога в один нельзя — это разные правила.
- **Семантика границы**: «не больше 400 000» трактуем как ≤ 400 000 (включительно). Если заказчик имел в виду строгое неравенство — граничный тест 400000 сломается; подтвердить.
- **Смягчение reject**: если трактовать как «пробег > 400 000 → review всегда», то reject при LTV 95 и пробеге 410 000 стал бы review — смягчение риска. План этого не делает (открытый вопрос).
- **Сигнатура `decide()`** меняется — сломает внешние вызовы, кроме `AssessmentService` (других в репозитории нет, подтверждено разведкой). Тесты `DecisionEngine` потребуют обновления конструктора.
- **Докблок vs код**: в `DecisionEngine` докблок уже расходится с кодом по границе `<=`/`<` (code_map.md, п.1). При правке докблока не «затереть» нюанс, а синхронизировать с реальным поведением.
- **Seed-данные**: все учебные авто в `db/seed.sql` — пробег ≤ 296 000, новое правило на них не сработает, поведение API по существующим данным не изменится.
- **Не входит в задачу**: связь пробега с возрастом, влияние пробега на лимит, LOAN-12 (LTV по возрасту), изменение `max_mileage_km`, фронтенд (пробег в ответах `create`/`ltv` не возвращается и не добавляется).
