## Факты по проекту

- Идентификатор клиента — `applicant_ref VARCHAR(32)` (`db/schema.sql:6`), из тела запроса, по умолчанию `CL-ANON` (`ApplicationController.php:33`).
- Статусы — `ENUM('new','decided','cancelled')` (`db/schema.sql:9`); код пишет только `decided` (`ApplicationRepository.php:32`); эндпоинта закрытия нет (`AppFactory.php:48-56`).
- `save()` — три INSERT без транзакции (`ApplicationRepository.php:24-58`).
- Ответы сейчас: 201 и 422 `{"errors":{...}}`; фронт показывает только `data.errors` (`frontend/app.js:54-58`).

## Блокеры и решения человека

Analyst остановил пайплайн до реализации: критических бизнес-правил (B1, B2) в источниках нет, выдумывать их запрещено постановкой.
Решения человека (2026-10-29):

| Блокер | Решение |
|---|---|
| B1 активная / закрытая | Активная — `new` и `decided`; закрытая — `cancelled` |
| B2 закрытие | Новый эндпоинт отмены: `POST /api/applications/{id}/cancel` → `status = 'cancelled'` |
| B3 без `applicant_ref` | Анонимный запрос (поле не передано, `CL-ANON`) под защиту не попадает; существующие тесты не трогаем |
| B4 нормализация | Без нормализации: сравнение по точному значению |
| B5 формат ответа | 409 с телом `{"errors":{"applicant_ref":"..."}}`; невалидный запрос — 422, приоритет у 422 |
| B6 схема и scope | Разрешено: STORED generated column + UNIQUE в `db/schema.sql`, отдельный файл миграции для существующих баз, транзакция в `save()` |

## AC (после решений)

- **AC-1.** Первый валидный `POST /api/applications` клиента без активных заявок → 201, тело как раньше; в БД одна активная заявка.
- **AC-2.** Повторный валидный POST того же `applicant_ref` при активной заявке → 409 `{"errors":{"applicant_ref":…}}`; новых строк в `applications`, `vehicles`, `decisions` нет.
- **AC-3.** После `POST /api/applications/{id}/cancel` (статус `cancelled`) новый POST того же клиента → 201.
- **AC-4.** N ≥ 2 **одновременных** POST одного клиента → ровно один 201, остальные 409, в БД одна активная. Только реальная параллельность (отдельные процессы и PDO), иначе НЕ ПРОВЕРЕНО.
- **AC-5.** Разные `applicant_ref` друг друга не блокируют.
- **AC-6.** Невалидный запрос → 422 с прежним телом, строк не создаёт (в том числе повторный).
- **AC-7.** `POST /api/ltv` не меняется.
- **AC-8.** Существующие тесты проходят, в том числе повторный прогон на той же БД (аноним `CL-ANON` под защиту не попадает).
- **AC-9.** Без коммита, push и деплоя внутри пайплайна; `rules.php` и числовые ожидания тестов не меняются; конвенции `AGENTS.md`.

## План (после решений)

1. `db/schema.sql`: колонка `active_applicant_ref` = `IF(status IN ('new','decided') AND applicant_ref <> 'CL-ANON', applicant_ref, NULL)` STORED + `UNIQUE`.
   Отдельный файл миграции для существующих баз с предпроверкой дублей.
2. Доменное исключение рядом с `ValidationException`.
3. `ApplicationRepository::save()` — транзакция; нарушение уникального индекса (1062, имя индекса) → `rollBack` и доменное исключение. Метод `cancel(int $id)`.
4. `ApplicationController::create()` → 409; новый маршрут и действие `cancel`.
5. Список активных статусов — одна константа в коде, согласованная с DDL.
6. Тесты: AC-1, AC-2, AC-3, AC-5, AC-6 — feature-тесты на MySQL; AC-4 — параллельные процессы с отдельными PDO.
