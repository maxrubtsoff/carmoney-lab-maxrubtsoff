# План MILEAGE — правило «пробег ≤ 400 000 км, иначе review»

Задача: в расчёт решения по заявке добавить правило — если пробег авто больше
400 000 км, итоговое решение должно быть `review` (даже если по LTV было бы
`approve` или `reject`). Ниже — план реализации. Код в рамках этой задачи не
меняется.

Сверка со спекой `docs/spec/spec_MILEAGE.md`: спека (по `docs/intent/grill_MILEAGE.md`)
закрывает все пять вопросов из раздела «Вопросы» ниже — статус обновлён там. Из
REQ/AC в план добавлено то, чего он не покрывал: граница `500000`/`500001`
(AC-09/AC-11), второй эндпоинт `POST /api/ltv` (REQ-MILEAGE-07, AC-12, AC-13) и
LTV-ветки при пробеге 399999 (AC-07/AC-08). Оба эндпоинта проходят через
`AssessmentService::assess()` (`ApplicationController::save` и
`ApplicationController::ltv`, маршруты в `AppFactory.php:52-53`), поэтому
правило достаточно вставить в `decide()` — оно подействует в обеих точках.

Контекст (свежо с `docs/setup/code_map.md` и чтения файлов):

- Решение выбирается в `backend/src/Domain/DecisionEngine.php::decide(float $ltv)`
  единственно по LTV; пробег на решение сейчас не влияет.
- Пробег проверяется только в валидаторе
  (`backend/src/Domain/ApplicationValidator.php:43-46`) на диапазон
  0…`rules.vehicle.max_mileage_km` (= 500 000) — это валидация, на 422 она
  завершается без решения.
- В `backend/config/rules.php` порога 400 000 нет, есть только
  `vehicle.max_mileage_km = 500000` (другая сущность, валидационный потолок).
- Сборка оркестратора — `backend/src/AppFactory.php:30-39`. Тесты — `tests/Unit/DecisionEngineTest.php`,
  `tests/Unit/AssessmentServiceTest.php`.

Точка вставки (по коду): порог в `rules.php`; проверка в `DecisionEngine` после
текущих веток по LTV; проброс пробега из `AssessmentService::assess()` в
`decide()`. Это «вариант A» из code_map.md, п. 2.

## Шаги реализации

По порядку:

1. Добавить в `backend/config/rules.php` в секцию `vehicle` ключ
   `mileage_review_above_km = 400000` (REQ-MILEAGE-01; вопрос о имени ключа
   закрыт спекой, «интервью 4»).
2. Расширить конструктор `DecisionEngine`: принимать порог пробега (int)
   дополнительно к LTV-порогам; сохранить в приватное свойство; обновить doc-блок
   класса (комментарий над классом описывает только LTV — добавить строку про
   пробег).
3. Изменить сигнатуру `decide(float $ltv, int $mileage): string`. **Внимание:**
   текущий метод — три ранних `return` (approve/review/reject), поэтому просто
   дописать `if ($mileage > $threshold) return REVIEW;` после них — мёртвый код,
   он никогда не выполнится. Нужно вычислить LTV-решение в переменную (например,
   `match`), затем — до `return` — проверить пробег и при превышении вернуть
   `REVIEW` вместо переменной; иначе вернуть переменную. Так порядок проверок
   (LTV → пробег) и перекрытие любого решения, включая reject → review,
   сохраняются (REQ-MILEAGE-03, «интервью 3»).
4. В `AssessmentService::assess()` (строка 33) пробросить `(int) $input['mileage']`
   вторым аргументом. `$input['mileage']` уже приходит из валидатора как int.
5. В `AppFactory::create()` (строка 37) передать порог пробега в `DecisionEngine`
   из `$rules` (новая секция или ключ, см. вопрос 1).
6. Обновить `tests/Unit/DecisionEngineTest.php`: setUp создаёт движок с порогом
   пробега 400 000; текущий `testDecidesByLtv` адаптировать — вызывать
   `decide($ltv, 0)` (пробег ниже порога не влияет); добавить новый DataProvider
   `mileageOverrides` и тест `testMileageAboveThresholdForcesReview`.
7. Добавить в `tests/Unit/AssessmentServiceTest.php` три новых теста на
   пограничные значения (см. раздел Тесты). LTV во всех трёх — в зелёной зоне
   (≈50.0), чтобы без нового правила было бы `approve`, а с правилом —
   `review`.
8. Прогнать `make lint` и `make test`. Не править существующие ожидания
   тестов ради зелёного прогона (по AGENTS.md п.5).
9. Прогнать `make up` и проверить оба эндпоинта (REQ-MILEAGE-07) вручную на
   пробеге 400 001 км с LTV ≈ 50 — ожидаем `decision: "review"`:
   - `POST /api/applications` — HTTP 201, `decision: "review"`,
     `approved_limit: 0`, заявка сохранена и видна с этим решением в
     `GET /api/applications/{id}` (AC-MILEAGE-13);
   - `POST /api/ltv` — HTTP 200, `decision: "review"`, `approved_limit: 0`,
     заявка не сохраняется (AC-MILEAGE-12).
10. Добавить Feature-тесты на оба эндпоинта (см. раздел Тесты, REQ-MILEAGE-07):
    если в `tests/Feature/` нет обвязки HTTP — уточнить у человека, как её
    поднять, самодельный харнесс не изобретать.

## Тесты

Граничные значения (отдельной строкой, как требует инструкция):

- пробег `399999` — ожидание `approve` (LTV в зелёной зоне; ниже порога).
- пробег `400000` — ожидание `approve` (на самой границе; правило
  «больше 400 000», не «больше или равно» — это закреплено в задаче).
- пробег `400001` — ожидание `review` (выше порога на 1), `approved_limit = 0`.
- пробег `500000` — ожидание `review` (верх валидного диапазона, окно действия
  правила 400 001…500 000; AC-MILEAGE-09).
- пробег `500001` — ожидание HTTP 422 с ошибкой `mileage` = «Пробег от 0 до
  500000 км» до расчёта решения — это валидационный потолок
  `vehicle.max_mileage_km`, не `review` (AC-MILEAGE-11, REQ-MILEAGE-05).
- пробег `-1` — ожидание HTTP 422 с той же ошибкой (AC-MILEAGE-11).
- пробег пустой/не передан — отдельно: валидатор сейчас трактует отсутствие
  поля как `-1` и бросает `ValidationException` → HTTP 422 (см. «Вопрос 4»).
  Поведение не меняем: «пустой пробег» — это всё ещё валидационная 422, а не
  `review` (AC-MILEAGE-10, REQ-MILEAGE-05); текст ошибки — «Пробег от 0 до
  500000 км».

Дополнительные кейсы (покрытие взаимодействия правил):

  - LTV ≈ 50 (approve-зона), пробег 400001 → `review` (правило понижает approve).
  - LTV = 70.0 (review-зона), пробег 400001 → `review` (без изменений;
    AC-MILEAGE-06).
  - LTV = 95.0 (reject-зона), пробег 400001 → `review` (правило перекрывает
    reject → review, REQ-MILEAGE-03, AC-MILEAGE-05).
  - LTV = 70.0, пробег 399999 → `review` (LTV-ветка review без изменений,

  - LTV = 95.0, пробег 399999 → `reject` (LTV-ветка reject без изменений,

  - LTV ≈ 50, пробег 500000 → `review` (верх окна правила, AC-MILEAGE-09).
- Существующие тесты `DecisionEngineTest::ltvValues` адаптировать вызовом
  `decide($ltv, 0)` — 0 км ниже 400 000, не влияет, ожидания прежние.
- `AssessmentServiceTest` — тесты: `testApprovesAtMileageBelowThreshold`
  (пробег 399999, LTV 50), `testApprovesAtMileageBoundary` (пробег 400000,

- REQ-MILEAGE-07, оба эндпоинта — Feature-тесты (AC-MILEAGE-12, AC-MILEAGE-13):

## Риски

Что может сломаться / требует внимания:

- Существующая проверка `max_mileage_km = 500000` остаётся в `ApplicationValidator`
  без изменений. Новый порог 400 000 — **отдельный** ключ, он не должен
  затронуть валидационный потолок 500 000. Если случайно завязать одно на
  другое, валидация начнёт резать заявки на пробеге 400 001 как 422 — это
  не то поведение, которое просит задача.
- `DecisionEngine::decide()` сейчас — единственный потребитель `ltv`.
  Расширение сигнатуры требует синхронного изменения всех вызывающих сторон:
  `AssessmentService::assess()` (строка 33) и `DecisionEngineTest` (строка 23).
  Если сигнатуру расширить, а вызовы забыть — PHPUnit провалится.
- Существующий тест `DecisionEngineTest::testDecidesByLtv` (строка 20-24)
  сейчас вызывает `decide($ltv)` — с новой сигнатурой он упадёт на
  ArgumentCountError. Не «чинить» правкой ожиданий: корректно — добавить
  второй аргумент в вызов.
- Тест `AssessmentServiceTest::testApprovesLowLtvAndSetsLimitToRequestedAmount`
  использует `mileage = 96000` (строка 38) — это ниже порога 400 000, на
  approve-зону не повлияет. Если кто-то «оптимизирует» payload() и поднимет
  mileage выше — тест молча сменит поведение. Не трогать payload() без
  явной причины.
- Правило `mileage > threshold` пишем именно как строгое `>`, чтобы граница
  400 000 осталась approve. Если написать `>=` — граница станет review, и
  тест `testApprovesAtMileageBoundary` провалится. Это противоречит формулировке
  задачи («не больше 400 000»).
- **Мёртвый код в `decide()`.** Метод сейчас — три ранних `return`; проверка
  пробега, дописанная буквально «после» них (как в первой версии этого плана),
  физически не выполнится — управление уже вернётся из одной из трёх веток
  LTV раньше, чем дойдёт до этой строки. Красные тесты на 400001/500000
  останутся красными и после «реализации» — это будет выглядеть как готовый
  код, который на самом деле не работает. Исправление: см. шаг 3 (решение в
  переменную, проверка пробега — перед возвратом).
- REQ-MILEAGE-07 требует правило в обеих точках расчёта. Оба эндпоинта
  (`POST /api/applications` и `POST /api/ltv`) идут через один
  `AssessmentService::assess()`, так что после правки `decide()` правило
  действует автоматически в обеих. Риск: если в `ltv`-эндпоинте когда-нибудь
  появится отдельный путь расчёта решения (мимо `assess()`), правило там
  потеряется — Feature-тесты AC-MILEAGE-12/13 это ловят.
- AGENTS.md п.5: пороги и формулы в `rules.php` и ожидания тестов не меняются
  ради зелёного `make test`. Если риск-менеджмент скажет «порог 350 000» —
  остановиться и уточнить у человека.
- Что **не входит** в эту задачу и не делается без отдельной задачи:
  - Не меняем `ApplicationValidator` (валидация ≠ решение).
  - Не трогаем `LtvCalculator`, `VehicleAge`, `VinValidator`.
  - Не заводим поле `mileage` в БД-миграцию (оно уже есть в `vehicles.mileage_km`,
    см. code_map.md п. 3).
  - Не правим `frontend/` (форма уже шлёт `mileage`).
  - Не делаем «только понижение approve→review» против «перезапись любого
    решения» — это вопрос к заказчику (см. ниже).
  - Не меняем существующее поведение на границе LTV 60.0 (строгое `<` vs
    `<=` — известное расхождение между кодом и doc-блоком, не наша задача).
