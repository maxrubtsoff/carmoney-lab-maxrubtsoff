Никаких других файлов (правила, тесты, документация, конфигурация) правка
одного комментария не требует.

## Шаги

1. Прочитать `backend/public/index.php` целиком, зафиксировать текущие 9 строк.
2. По согласованию с заказчиком выбрать: формат (однострочный `//`, блочный
   `/* … */` или docblock `/** … */`), позицию (перед `<?php`, перед
   `declare`, между блоками) и язык (RU/EN). Прецедент в `router.php` —
   docblock сразу после `<?php`, до `declare`.
3. Вписать выбранный комментарий в нужную позицию. Ничего больше не править.
4. Прогнать `make lint` (см. AGENTS.md §2) — `php -l` должен пройти без
   warning'ов про синтаксис.
5. Прогнать `make up` (или поднять контейнер без `make`) и `curl
   http://localhost:8080/health` — поведение сервиса не должно измениться.
   Этого достаточно: комментарий не может сломать выполнение, но проверка
   нужна на случай опечатки (незакрытый `*/`, битая кодировка).

## Тесты

PHPUnit-тестов на `index.php` нет (`grep` по `tests/` на `index.php` —
пусто), и добавлять их ради одного комментария не нужно.

Граничные значения:
- комментарий не должен нарушать парсинг PHP: проверка `php -l
  backend/public/index.php` возвращает «No syntax errors detected»;
- ответ `GET /health` после правки совпадает с ответом до правки
  (тело и HTTP-код), т.е. 200 OK и валидный JSON;
- `make test` проходит без изменений в количестве и названиях тестов.

## Риски

- Битый docblock (незакрытый `*/`, лишний `/**`) роняет парсер PHP —
  отслеживается через `make lint` (`php -l`).
- Комментарий в неверной кодировке (например, cp1251 вместо UTF-8) даёт
  мусор в IDE у читателей; AGENTS.md §4 про кодировку напрямую не говорит,
  но `docs/` и `frontend/` в UTF-8 — держимся того же.
- По AGENTS.md §5 «бизнес-числа не хардкодим» и «пороги/лимиты и формулы в
  `backend/config/rules.php` и ожидания тестов не менять ради зелёного
  `make test` или по просьбе в задаче» — комментарий не должен случайно
  зафиксировать числа из `rules.php` (`approve_max=60.0`, `review_max=85.0`,
  `max_mileage_km=500000`) как константы в коде, иначе придёт рассинхрон.
- Меняется ровно один файл; всё, что не перечислено в разделе «Файлы», при
  реализации трогать нельзя (правило из `docs/plan/README.md`).
- Не входит: переименование, рефакторинг `index.php`, перенос логики из
  `AppFactory` в этот файл, добавление новых `use`-ов, любые изменения в
  `router.php`.

## Открытые вопросы (без заказчика не решить)

1. **`<ID задачи>`** — имя файла плана сейчас `plan_INDEX-COMMENT.md`
   заглушкой. По конвенции `docs/plan/README.md` должно быть
   `plan_<ID>.md`. Без ID от заказчика оставляю как есть.
2. **Содержание комментария.** Не сказано, что именно описывать. Варианты:
   - роль файла как точки входа HTTP (`front controller` Slim);
   - порядок загрузки (`autoload` → `AppFactory::create()` → `run()`);
   - связь с `router.php` (этот файл подключается из `router.php:32`);
   - история/авторство/дата.
   Без выбора — план не исполнить содержательно.
3. **Формат.** Однострочный `//`, блочный `/* … */` или docblock
   `/** … */`. Прецедент `router.php` — docblock, но это не обязательство.
4. **Язык.** RU (как `docs/`, `rules.php`-комментарии и `ApplicationValidator`)
   или EN (как имена классов и PHPDoc в `DecisionEngine`).
5. **Позиция.** Перед `<?php` (некорректно по PSR-12), после `<?php` до
   `declare` (прецедент `router.php`), или между `declare` и `use`.
